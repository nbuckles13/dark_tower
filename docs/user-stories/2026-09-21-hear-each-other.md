# User Story: Hear Each Other (N+1 Participants)

**Date**: 2026-09-21
**Status**: Ready
**Participants**: auth-controller, global-controller, meeting-controller, media-handler, client, database, protocol, infrastructure, security, test, observability, operations

## Story

As a **participant**, I want **to join a meeting alongside up to N other participants from a browser and hear each of them while each of them hears me — where N is a configurable number of audio receive slots filled in join order, a host-side server mute silences a participant for everyone, and a participant leaving stops being able to hear the meeting** so that **the ADR-0036 media path is proven as a multi-party meeting with the enforcement (server mute at MH ingress) and key hygiene (leave-debounced KEK rotation) that make it safe to use with people who are not me**.

**Governing design**: `docs/decisions/adr-0036-media-flow.md` (Accepted). This is story 2 of the ADR-0036 arc (*Addendum — Planned Story Arc*, the arc's single maintained home). Scope as recorded there: **N+1 participants hear each other**, N = a configurable number of client audio receive slots (N may be 1 or larger), **static fill (join order), not speaker-based selection**; plus **server mute** (§7, enforced at MH ingress) and **KEK rotation on leave** (§4, debounced to at most once per W). Enabled by story 1's deliberately general N=1 assignment. **Attestation (`cnf` thumbprint, AC-blessed identity key) is NOT in this story** — the addendum pulled it into its own separately-sequenced story; story 1's file predates that re-scope where it says otherwise.

**Inherited from story 1** (`docs/user-stories/2026-08-27-hear-yourself-through-handler.md`, "Deferred to later stories" and "Scope decisions"): the egress-budget chain with its settled specification (`MH_EGRESS_BUDGET_BPS`, per-media-kind per-stream cost keys, derived stream ceiling populating `max_streams` to GC, MH-side stream admission, rejection-ratio threshold gauge, exhaustion alert and runbook scenario); peer-key validation; KEK-push behaviour; leave-debounced KEK rotation and its exposure window; `sender_id` rotate-and-reissue; "no way to disable the media path short of a redeploy" as an operations scope item. Two `docs/TODO.md` items are triggered by this story's egress-budget work: MH's unbounded registered-meeting count, and MH never reclaiming an ended meeting's routing entry.

## Requirements

Confirmed by the user 2026-09-22 after one discussion round. Three code facts shaped the list: the MC→MH fan-out data plane and the client's per-sender crypto state are already general (story 1 built them N-wide); the server-side slot cap `MC_MAX_RECEIVE_SLOTS` already exists; and the client↔MC signalling proto is already complete (KEK push, server mute, seven slot states all on the wire, unused). The new wire surface is two additive items on the internal MC→MH contract.

**Headline: N+1 hear each other**
- [ ] R-1: N+1 distinct accounts join one meeting from N+1 browsing contexts on one machine (one distinct account each; separate profiles recommended) via `dev-web.sh` and each hears every other. N is a client-configured audio receive-slot count (≥1), capped server-side by the existing MC cap; a client declaring more than the cap fails loudly rather than presenting as one silent participant. *(client, infrastructure, meeting-controller)*
- [ ] R-2: Slots fill in join order from senders the subscriber shares a connected handler with (R-33), one MC-pinned source per slot, no reselection. When senders outnumber a subscriber's slots the earliest joiners occupy them; unfilled slots report the explicit "fewer sources" state on the wire and render as an under-filled grid, never a spinner. *(meeting-controller, client, protocol)*
- [ ] R-3: **Loopback is removed.** No participant ever hears their own audio; a solo participant hears silence with explicit "fewer sources" slot states. Story 1's loopback browser env-test and demo are superseded by the two-sender scenarios; the MH-level Rust loopback test stays because MH executes edges without knowing one is reflexive. Story 1's R-1 gets a superseded note. *(meeting-controller, client, test)*
- [ ] R-4: **Slot stability.** A slot carrying a participant who did not leave is never changed by another participant's join or leave. On a join, the joiner fills the first empty slot of each existing subscriber and nothing else moves. On a leave, only the freed slot changes, refilled by the earliest-joined previously-unassigned sender if any. Each change is an immediate recompute and re-push to the handler carrying the monotonic policy generation (which advances only when the assignment changed) and confirming MH's applied-generation echo; existing subscribers receive updated slot assignments; no unrelated participant's audio stalls across the transition. Cadence, jitter and connectivity-loss re-assert stay in story 4. *(meeting-controller, media-handler)*
- [ ] R-5: The client concurrently verifies, replay-checks, decrypts, decodes and mixes N distinct senders; a bad frame from one sender is a counted drop that never silences or corrupts another sender's audio. *(client)*
- [ ] R-6: A join into a meeting that already has a healthy assignment succeeds without re-running or failing on handler selection (today it re-selects, discards the result, and fails if the candidate pool is momentarily empty). Stickiness is meeting → handler SET, programmed once via `assign_meeting` (up to two handlers, frozen at first join) and proven by test; every participant is offered the whole set and connects to all of it it can (R-33). *(global-controller)* *(amended in design)*
- [ ] R-7: **Test-tone send mode.** A config-driven, never-default client option replaces microphone capture with a constant tone whose frequency is derived from the participant, so "I hear A and C but not B" is audible by ear and checkable by machine. One mechanism serves the automated env-tests (R-30) and the manual demo, and removes the one-microphone-N-tabs feedback problem. *(client, test, security for the gating)*

**Server mute**
- [ ] R-8: Only a host-role participant can server-mute or lift a server mute on another participant. Host today means the meeting creator, singular, derived by GC and stamped into the meeting token; guests can never be host; MC reads it from the token. The requester is identified from the authenticated connection, never from a message field; a non-host attempt is refused generically and counted; requests are rate-bounded per connection. No AC change. *(security, auth-controller, meeting-controller)*
- [ ] R-9: A server-muted participant's media reaches no subscriber even if their client keeps sending: MH drops that source at ingress, counted under its own reason, keyed by sender (MH cannot read the stream component, which sits inside the encrypted key id; sender-scoped is exact for audio-only) so MH stays type-blind. *(amended in design)* The mute rides the full registration snapshot so it survives a re-assert or MH restart; an authorized unmute restores forwarding within one policy generation. MC counts server mute separately from client mute. *(media-handler, protocol, meeting-controller, observability, operations)*
- [ ] R-10: A server-muted participant cannot clear it themselves; client mute and server mute compose independently; the mute survives a reconnect within the grace window but not a fresh rejoin, and is never described as a ban. *(security, client)*
- [ ] R-11: Every client renders server-muted state from the wire (the single "source muted" slot state covers both client and server mute; the roster carries who muted whom), visibly distinct from client mute, and the host has a UI affordance to mute and unmute. *(client, protocol)*

**KEK rotation on leave**
- [ ] R-12: Every roster removal triggers a KEK rotation, debounced to at most once per W measured from the oldest un-rotated removal; the new KEK and generation reach exactly the members present after removal, with the leaver unreachable by construction. W is MC configuration, default 60 s. *(meeting-controller, security, infrastructure)*
- [ ] R-13: **ADR correction.** A leaver's exposure is W plus one transmit-key interval, not W, because receivers cache unwrapped transmit keys. Fix: §4's transmit-key trigger table gains "the meeting KEK rotated", so senders re-wrap at rotation and the stated W bound holds. No doc or test states the bound as W until it lands. *(security)*
- [ ] R-14: Receivers hold at most one previous KEK generation for a bounded window so in-flight frames still open and no active sender's audio gaps across the switch; other generations are dropped and counted. The window is derived at the receiver from W, which MC carries on the wire, so the receiver never runs zero retention and the relationship to W is satisfied structurally rather than by a check; a zero or absent W is floor-substituted, counted and logged loudly, never a hard failure (rollback). *(client, operations, security)* *(amended in design: was a client knob with a loud consistency check)*
- [ ] R-15: A reconnecting participant receives the current KEK without triggering a rotation; a flapping client can force no more than one leave-triggered rotation per W and cannot wedge the sender namespace (R-16's rotation is immediate and exempt from W). Flapper eviction does not ship; the recorded residual is the flapper's join-path cost, made visible by a namespace-consumption maximum. *(meeting-controller, security, operations)* *(amended in design)*
- [ ] R-16: When the 16-bit sender space would exhaust, MC rotates the KEK and reissues sender ids from a fresh namespace instead of rejecting admission; no key id is reused under one KEK. **An MC integration test drives the allocator through the full space and asserts rotate-and-reissue occurs and admission never fails**, so this path is exercised on every run rather than once in production. *(meeting-controller, security, test)*
- [ ] R-17: A participant joining after a rotation opens current frames; a leaver holding the old KEK cannot open post-rotation frames (client integration test, since a departed browser tears down). *(client, test)*

**Cross-participant identity**
- [ ] R-18: Attribution derives only from the key id's sender component resolved against that sender's roster key; a peer with a missing, wrong-width or unimportable roster key has frames dropped and counted; a roster update rebinding a live sender to a different key purges that sender's cached transmit keys only; replay state is retained, because MC never legitimately rebinds a live sender and clearing the window would permit a rebind-back replay. *(amended in design)* The roster key stays trust-on-first-use and nothing added may call it attested. *(security, client, meeting-controller)*

**Handler capacity and reclamation**
- [ ] R-19: The egress-budget chain lands per story 1's settled spec: one bandwidth budget plus per-media-kind per-stream costs; the derived stream ceiling is the same value MH enforces at admission and advertises to GC in the existing field; budget, ceiling and rejection-ratio gauges; one configured threshold read by both alert and enforcement; `MH_MAX_STREAMS` retired over two deploys (code read, defaults, `.env.example` and DEVELOPMENT.md now; ConfigMap key and refs marked retired with a scheduled removal, because rollout undo restores the Deployment's key reference without the ConfigMap); fail-closed low default with a refuse-to-boot floor at a derived ceiling of 2. *(amended in design)* GC placement stays soft (documented); MH admission is the hard backstop. *(media-handler, infrastructure, global-controller, database, observability)*
- [ ] R-20: MH releases an ended meeting's routing state on an explicit MC teardown signal, so a long-running pod admits a new participant exactly as a fresh pod does. This adds a lifecycle RPC to `MediaHandlerService`; **ADR note** narrows the "one RPC by design" invariant to forwarding policy. *(protocol, meeting-controller, media-handler, security, operations)*
- [ ] R-21: MH publishes edge occupancy, edge limit and registered-meeting count as gauges with a headroom warning; the registered-meeting count is capped by a required key with counted rejections (an empty egress set is legal, so the budget is structurally blind to concurrent empty meetings). *(amended in design)* *(observability, media-handler, operations)*
- [ ] R-22: The four §8 policy-bound MH keys land in the ConfigMap on every workload as required reads, framed as resource guards never capacity. *(amended in design: required, manifests first)* *(infrastructure, operations)*

**Configuration, deployment, rollback**

**Multiple handlers (added 2026-09-22 from the user's comment)**

## Design

**Requirement amendments made during design** (each traceable; the requirement text above is amended in place where marked):
- **R-9** "keyed by sender and stream" → **sender-only.** MH cannot read a datagram's publisher stream number (it is inside the opaque SFrame key id, `crates/media-protocol/src/frame.rs:106-126`); a stream field would be enforced nowhere. Audio-only story 2 has one stream per sender, so sender-scoped is exact; per-kind mute will key on transport when video lands (story 3). *(protocol, media-handler)*
- **R-14** **W is carried on the wire** (`kek_rotation_debounce_seconds` on the KEK push and the join-shaped reconnect response) and the retention window is **derived at the client** as `min(W/2, ceiling)`. It is not a client knob: the client cannot validate against W at startup, so a client knob degrades to a first-push runtime check and permanent silence. Deriving retention from W at the consumer makes retention < W structural, so MC does no retention check. The ceiling exists because retention serves frames in flight, a latency-scale need, and must not scale with W without bound. The client keeps the retention-exceeds-re-wrap-latency check, and it floor-substitutes, counts and WARNs on a zero or absent W, never hard-failing. *(Amended at story-2 task 1: this bullet previously described an MC-derived `previous_generation_retention_ms` that MC validated; the contract carries W instead, per decisions 9/10.)* *(operations, security, client, meeting-controller)*
- **R-15** the "at most one rotation per W" bound applies to **leave-triggered** rotations; **R-16** exhaustion-triggered rotation is **immediate and exempt from W** (debouncing a fail-closed admission condition would stall joins for up to W) and self-limited to once per 65,536 admissions. Flapper eviction does **not** ship — recorded decision (below). *(lead, security, operations, meeting-controller)*
- **R-18** narrowed: a rebind purges the sender's **cached transmit keys only**; **replay state is retained** (contexts, bitmaps, generation high-water), because MC never legitimately rebinds a live sender (a new key always means a new sender id) and clearing the window would permit a rebind-back replay. Security authored the original phrase and the correction. *(security)*
- **R-19** "deleted from all four places" → **two-deploy retirement**: this story deletes the code read, `DEFAULT_MAX_STREAMS`, the config field, `.env.example` and `docs/DEVELOPMENT.md`; the ConfigMap key and both `configMapKeyRef` entries stay marked retired-pending-removal with a scheduled TODO. `kubectl rollout undo` restores the Deployment's `configMapKeyRef` but not the ConfigMap, so deleting the key first turns rollback into `CreateContainerConfigError`. The DB `DEFAULT 1000` stays (no migration; unreachable because the budget key is required). *(lead, infrastructure, operations, database)*
- **R-21** decided: a **`MH_MAX_REGISTERED_MEETINGS` cap ships**, with counted rejections — reclamation bounds ended meetings but an empty egress set is legal, so concurrent empty meetings are a surface the budget is structurally blind to. *(media-handler, operations)*
- **R-22/R-23** all new MH keys (budget, two costs, threshold, meeting cap) **and** the four §8 policy keys are **required** reads; manifests land first (task 2 precedes task 8). Required is what gives `dt-guard env-config` rule-1 coverage; browser-side knobs are outside that guard, and after design only **client N** (`VITE_DT_RECEIVE_SLOTS`) is browser-side (test-tone is a build define; retention is MC-pushed). *(infrastructure, media-handler)*
- **R-29** the operator-lever sentence for server mute reads "no operator-facing API or tooling", never "impossible": mute rides the MC→MH contract, which authorizes on scope alone, so a `service.write.mh` holder can set or clear it (MH 19's second arm). Adds the F13/F14 revisions, MH Scenario 17's loopback subsection, MC Scenario 8, and the new MH deployment config-failure triage section. *(security, operations)*
- **R-27** the missing-key threshold **stays at 5 % / 15 m** (≈25× margin once retention and re-wrap exist); the finding is a blind spot — a fleet-wide ratio hides one client whose push always fails — with MC's per-recipient push counter recorded as the compensating control. Collector exporter sets `add_metric_suffixes: false`; `resource_to_telemetry_conversion` stays off (the contract labels are per-datapoint attributes). *(observability, infrastructure, client)*

**Names fixed by this plan** (single source for tasks that run without each other): `MC_KEK_ROTATION_DEBOUNCE_SECONDS` (W, required, 60); `VITE_DT_RECEIVE_SLOTS` (client N); `__DT_TEST_TONE__` (Vite build-time define for test-tone mode); `MH_EGRESS_BUDGET_BPS`, `MH_STREAM_COST_AUDIO_BPS`, `MH_STREAM_COST_VIDEO_BPS`, `MH_EGRESS_REJECTION_RATIO_THRESHOLD`, `MH_MAX_REGISTERED_MEETINGS`; `MH_MAX_MUTED_SOURCES_PER_MEETING` (MH, required, the per-meeting bound on the muted set); proto `MutedSource { sender_id }` on `RegisterMeetingRequest.server_muted_sources`, `EndMeeting(EndMeetingRequest{meeting_id, mc_id}) → EndMeetingResponse{acknowledged}` (mismatch → `FAILED_PRECONDITION`), `kek_rotation_debounce_seconds` (W, on `JoinResponse` and `MeetingKekUpdate`), `StreamAssignments.unreachable_sender_ids`; drop reason `server_muted`; MC metrics `mc_meeting_kek_generated_total{trigger}`, `mc_meeting_kek_pushes_total{outcome}`, `mc_meeting_kek_rotation_pending_age_seconds`, `mc_meeting_kek_rotation_window_seconds`, `mc_meeting_kek_rotation_overdue_threshold_seconds`, `mc_media_server_mute_requests_total{action,outcome}`, `mc_media_receive_slot_cap`, `mc_meeting_sender_ids_issued_max`; MH `mh_media_egress_edges`, `mh_media_egress_edges_limit`, `mh_media_registered_meetings`, `mh_media_meeting_teardowns_total{outcome}`, `mh_media_stream_admission_total{outcome}`, `mh_media_stream_admission_rejection_ratio` + `_threshold`, `mh_media_egress_budget_bytes_per_second{basis="unmeasured"}`, `mh_media_egress_stream_ceiling`; client `dt_client_media_active_receive_sources`, `dt_client_media_kek_generations_retained`, `dt_client_media_capture_source{mode}`, reason `kek_generation_stale`.

### Multiple handlers (R-33, ADR-0036 §9)
GC already selects a handler SET per meeting (up to two healthy handlers, weighted random, `services/mh_selection.rs`) and programs MC with it once via `assign_meeting` (repeated `MhAssignment`); the set is frozen at first join. Every client is offered the whole set (`JoinResponse.media_servers`) and connects to all of it it can — the client transport is active/active, as in story 1. MC learns each participant's connected handlers from MH's `NotifyParticipantConnected` / `NotifyParticipantDisconnected` (server-observed; identity from the validated token) and routes each publisher→subscriber pair through ONE handler both are connected to; a pair with no shared handler is unreachable, carried per subscriber in `StreamAssignments.unreachable_sender_ids` (protocol found the carrier gap: `SOURCE_UNREACHABLE` rides a declared slot with no sender and cannot name a peer; that state stays retained-but-unemitted). Which shared handler carries a pair is MC's choice — prefer co-location (fewest send targets per sender), keep edges stable while they remain valid — and nothing depends on a particular handler. A sender sends to every handler owning one of its edges (multi-handler send; the wire already carries `repeated SendTarget`). With everyone connected everywhere, everyone hears everyone; partial connectivity (A on both handlers, B on one, C on the other: A hears both, B and C only A) is the same rule, not a special case, and env-tests produce it with mock clients that connect to a subset of the handlers. MH needs no change (per-process routing snapshot, no peer-handler concept, per-pod budget and meeting count; `EndMeeting` fans out to every assigned handler); the muted set is filtered per handler to the muted senders that send to it; KEK rotation is per meeting across handlers. The receive path gains a slot-edge gate (today it decodes any verified rostered sender). mh-1 is already reachable from the host browser in Kind (hostPort 4436, own advertise address, shared pinned certificate, preflighted by `dev-web.sh`). No handler-to-handler cascade (future work). *(Corrected 2026-09-24: the original plan placed each participant on one handler round-robin and scoped its URL list to that handler; see Revisions.)*

### meeting-controller
The centre of the story. Story 1's `compute_assignment` is a pure recompute producing one egress stream per subscriber with all sources as candidates (the MH-selects model, story 5's shape); slot stability (R-4) cannot come from a pure recompute, so the meeting actor gains **per-meeting slot state**: per subscriber an ordered vector of optional sender ids sized to that subscriber's own declared count, plus a join-order sequence. Join fills each existing subscriber's first empty slot and moves nothing else; leave frees only the leaver's slot and refills it with the earliest-joined unassigned sender; a reconnect keeps its rank. A pure render turns the state into the existing `MeetingAssignment` — now one pinned candidate per egress stream. `subscribes_to` becomes non-reflexive (loopback removed). The receive-capability declaration is registered into the actor. The RegisterMeeting push generalises from first-participant-only to a full-snapshot re-assert on every structural change with the change-advanced generation and applied-echo confirm; a third driver re-emits full `StreamAssignments` to affected subscribers under a per-meeting bound. KEK rotation: `rotate()` on `MeetingKeyState`; debounced from the oldest un-rotated removal, never reset; hung on the roster-removal choke point so the leaver is unreachable by construction; retention derived from W and pushed; reconnect re-issues the current KEK idempotently; sender-id exhaustion becomes an atomic KEK-epoch reset (immediate, undebounced) with a full-space integration test; `MCSenderIdSpaceExhausted` retired. Server mute: the muted set in every snapshot; host-only apply and lift, requester from the connection, authority before target, refusal at dispatch and in the actor; `UnmuteRequest` only notifies; late joiners get replayed `ParticipantMuteUpdate`s. Teardown: `EndMeeting` after the actor stops pushes. Three tasks (6, 9, 11).

### media-handler
The N-edge fan-out data plane already exists (`forward_one` single-pass fan-out, `for_each_source`, atomic per-meeting `ArcSwap` swap) — story 2 proves it under runtime churn rather than building it. New: the egress-budget chain (required keys, bits converted once, ceiling = budget / max(cost) ≥ 1 enforced at admission beside the aggregate-edge guard and advertised to GC in `max_streams`; four gauges; one threshold for enforcement and alert; `MH_MAX_STREAMS` code read deleted); server mute as a sender-scoped ingress drop before decode with its own reason, riding the snapshot; `EndMeeting` releasing routing and session state with an `mc_id` ownership reject; edge/limit/meeting gauges and the meeting cap. MH stays keyless and type-blind; nothing new inside the forward-path deny scope. Two tasks (8, 10).

### client
Per-sender crypto state already exists (replay window, transmit-key cache, roster resolver keyed by sender). New: per-sender decoders mixed to one sink with fault isolation; a KEK holder of current + at most one previous generation honouring the MC-pushed retention, `meetingKekUpdate` wired; sender-side transmit-key rotation on KEK receipt (R-13); rebind purge (keys only); peer-key well-formedness drops. Test-tone send mode as a build-time define with sender-id-derived frequency and a bundle-absence proof; N from `clientConfig` via Vite env with loud over-cap failure and runtime-readable N and cap; three-layer per-slot receive counters on the test bus; active-source gauge as observed decode activity. Multi-participant UI with slot rows, distinct client-mute and server-muted-by-host indicators, host affordance; loopback env-test deleted; browser env-tests S1, S2, S3, S6-joiner and the two-part R-27 read-back. Three tasks (7, 12, 14).
