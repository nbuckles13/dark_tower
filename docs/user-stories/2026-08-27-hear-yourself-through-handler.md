# User Story: Hear Yourself Through the Handler

**Date**: 2026-08-27
**Status**: Ready
**Participants**: auth-controller, global-controller, meeting-controller, media-handler, client, database, protocol, infrastructure, security, test, observability, operations

## Story

As a **participant**, I want **to join a meeting from Windows Chrome, speak, and hear my own audio returned through the media handler, with mute silencing it instantly and unmute restoring it instantly** so that **every layer of the ADR-0036 media path (capture, encryption, signing, transport, handler forwarding, decryption, verification, playback) is proven end to end with one client before any second participant is involved**.

**Governing design**: `docs/decisions/adr-0036-media-flow.md` (Accepted). This is story 1 of the eight-story ADR-0036 series; it is deliberately loopback so a failure anywhere in the pipe is localised to one client. The story carries the ADR's details forward and adds none. Demo target: Windows Chrome via `scripts/dev-web.sh` against the Kind cluster.

**Acceptance framing, stated so it is not overclaimed.** No production Rust component seals, signs, verifies, or decrypts a media frame (MH is keyless, MC never encrypts), so the same TypeScript encrypts and decrypts in loopback and a self-consistent crypto error is invisible to the demo. "Every layer proven end to end" therefore means *wiring proven by the demo and browser env-test, crypto proven by the cross-language vectors* (R-7) — whose Rust reference generator is deliberately non-production and is the only independent check on the TypeScript crypto.

**Series plan** (each story ends in something a person can demonstrate in a browser): 1 hear yourself · 2 hear each other (attestation, second participant, server mute, KEK rotation on leave) · 3 see each other (video) · 4 survive a handler restart (§8 re-assert) · 5 a crowded room picks the right speakers (selection) · 6 two handlers, one meeting · 7 historical meeting debug (per-meeting/per-client quality records with a retention posture — an ADR-0036 §11 amendment) · 8 performance (targets, benchmarks, tuning).

## Requirements

**Headline**
- [ ] R-1: A participant joining from Windows Chrome via `scripts/dev-web.sh` grants microphone access and hears their own audio returned through MH. *(client, test)*
- [ ] R-2: Client mute stops all media leaving the device within one frame, asserted at the client transport seam (egress count stays flat) — never by absence of audible output; unmute resumes with no signalling round trip; the in-meeting view visibly indicates mute state, driven by the SDK's client-mute state and never inferred from frame absence. MC keeps the send directive active and unchanged across the cycle. *(client, meeting-controller, security)*
- [ ] R-3: A mute longer than the keepalive interval is followed by an unmute that restores audio on the same connection — no reconnect, no rejoin. *(operations, infrastructure)*
- [ ] R-4: The loopback receive path resolves the signing key from the roster and runs the identical verify-then-decrypt path a peer frame would take; there is no branch that trusts a frame because this client signed it. *(security — Finding 1)*

**Wire format (§2)**
- [ ] R-5: Every media frame uses header v2 with a signed publisher region and a relay region MH may rewrite; the signature over publisher region + payload verifies independently of any relay rewrite. *(protocol, media-handler)*
- [ ] R-6: Decode fails closed in both codecs: undefined flag bits and unknown versions rejected; no skipped bytes; a declared payload above the wire maximum rejected before any allocation — including in the reader that calls decode; decode returns a slice, not a copy. *(protocol, security, test)*
- [ ] R-7: One canonical test-vector set gates both codecs with an executable drift guard that fails when Rust and TypeScript disagree; it includes a tamper pair, the insider-forgery vector (a frame under another sender's key id is rejected, not attributed — authored so it *would* decrypt if verification were skipped), and the wrong-key-id-wrap-ignored vector. The vectors are generated by a Rust reference implementation of the SFrame/sign/wrap construction, authored independently from the spec, deliberately non-production, and retained as the only check against a wrong-but-consistent TypeScript implementation; the key schedule is additionally gated against the external sframe-wg vectors. Vectors are a drift guard, not a freeze — the header may change across stories and the vectors are regenerated when it does. Fuzz corpus regenerated. *(protocol, test, security)*
- [ ] R-8: Stream sequence counts per (sender, stream), readable before decryption, never reset; key id encodes (sender, stream, generation) with generation monotonic **per sender**; hop sequence counts per (connection, media stream) only frames actually sent. *(protocol)*
- [ ] R-9: The publisher region carries a key-bearing flag and, when set, a fixed-size wrapped transmit key on every audio frame; forwarded unchanged by MH; no key material on the roster or across MC→MH. *(protocol, client)*

**Keys and crypto (§3, §4)**
- [ ] R-10: On admission MC issues the meeting KEK and its generation in the join response; the KEK is CSPRNG-generated, held only in the meeting actor's memory, never persisted, never logged, never sent to MH. *(meeting-controller, security)*
- [ ] R-11: The client generates its identity signing keypair before join and presents the raw Ed25519 public key; MC validates well-formedness (exact length) and publishes it on the roster **without a thumbprint check** — a stated gap closed by story 2; no identifier, field name, doc, or test may describe the roster key as attested, verified, or trusted (`identity_public_key` is the honest spelling). *(meeting-controller, security)*
- [ ] R-12: Every audio frame leaving the client is SFrame-encrypted (AES-256-GCM, per-(sender, stream, generation) transmit key, nonce synthesised from key id + stream sequence, RFC 9605 §4.4 key schedule under ciphersuite 0x0005) and Ed25519-signed; received frames are verified, decrypted, decoded and played; a frame failing any step is dropped, never played. *(client, security)*
- [ ] R-13: Receivers reject replays via a sliding window per (sender, stream, generation) that advances only on signature-verified frames; a wrapped key is accepted only for the key id of the frame carrying it; attributed sender identity derives from the key id's `sender_id` and nothing else; a transmit-key generation bump occurs within a loopback session. *(client, security)*
- [ ] R-35: A key id is never reused under one KEK — generation is monotonic per sender and never reset, **and** `sender_id` is never recycled while a KEK is live (MC allocates monotonically within 16-bit semantics — carried as proto uint32, range-checked — never recycles on leave, and rejects admission — fail closed, never warn-and-continue — if the 16-bit space would wrap; rotate-and-reissue lands with the rotation story). The 40-bit generation is effectively inexhaustible and carries no ceiling guard. Key id layout: `sender_id(16) | stream(8) | generation(40)` in the 64-bit SFrame KID — the user chose a 16-bit sender over 32-bit because the KID is capped at 64 bits and a 24-bit generation would be exhaustible in weeks-long meetings. Neither half is derivable from the other; the ADR states only the first. *(security — escaped planning)*

**Transport and handler (§1, §7, §8, §11)**
- [ ] R-14: MH declares its QUIC transport parameters from configuration — max concurrent uni streams, datagram send buffer **in frames of audio**, keepalive interval — validates at startup, refuses to start on an invalid value, and logs effective values. *(media-handler, infrastructure, operations)*
- [ ] R-15: MH forwards a client's uplink audio datagrams back to that client purely from MC-pushed policy — rewriting only the relay region, never decrypting or verifying, with no per-frame heap allocation. *(media-handler)*
- [ ] R-16: MC computes the loopback assignment with the general N=1 algorithm (no single-handler special case) and programs MH via the registration RPC carrying policy (edges; per-egress priority group, supersede-on-independent-frame, transport mode) and an output-derived generation; MH's response reports handler id, process-start epoch, echoed transport mode, and the **applied** generation; MC fails loudly on mismatch. One-shot push only; periodic re-assert is the restart story. *(meeting-controller, media-handler, protocol)*
- [ ] R-17: MC directs the client to produce one audio stream (encoding params, header v2, target set with datagram transport) and assigns the client's own audio to its declared audio slot with explicit slot state on the wire. *(meeting-controller, protocol)*
- [ ] R-18: MH's application egress queue bound trips before the transport ceiling; ingress enforces max payload before allocation, a bounded drop-oldest datagram queue, per-connection rate limits, and a server-side slot cap; every drop/reject is counted by reason. *(media-handler, security, test)*
- [ ] R-19: The SDK owns a bounded egress queue above the transport, drops oldest under pressure, and counts every send-side drop — observable by construction since MH cannot see it. *(client, observability)*
- [ ] R-20: Media ingress/egress are reachable only after the WebTransport meeting-token accept gate. *(security)*
- [ ] R-21: MH's drain window is derived from the pod's termination grace period; no second literal. *(infrastructure, operations)*
- [ ] R-22: `MH_MAX_CONNECTIONS` is set explicitly in the ConfigMap as a resource-exhaustion guard (its absence from every manifest is how a 10 000 default nobody chose went live). The egress-budget chain — budget key, per-stream costs, derived stream ceiling, gauges, admission enforcement — is deferred in full to story 2 with its settled specification recorded below. *(infrastructure, operations)*

**Telemetry (§11)**

## Design

### meeting-controller
Per-meeting actor generates a random AES-256 KEK (`ring::rand::SystemRandom`) with a u16 generation, in memory only. Join request carries the raw Ed25519 identity key; MC validates length and publishes it on the roster as `identity_public_key` with no thumbprint check (stated gap; same-keyholder consistency only). MC allocates a 16-bit `sender_id` per admission (proto uint32, range-checked) — monotonic, never recycled, reconnect keeps it, exhaustion rejects the join — returned in the repurposed `user_id` field with the KEK and generation. The general N=1 assignment yields one self→self audio edge; MC pushes it once via the reshaped RegisterMeeting (edge set, per-egress priority group / supersede off / datagram, output-derived generation) and confirms the echoed applied generation, feeding `mc_media_generation_divergence` from the applied value. Post-join dispatch handles the receive-capability declaration and emits the send directive (no priority group — an egress property) and the slot assignment keyed by `sender_id`; mute holds the directive. The empty target set is a computed output, never an operator lever. Task 2 owns the `RouteMedia` mock fallout in two MC integration tests. Extends the credential-leak semantic guard's check definition to KEK/transmit-key material.

### media-handler
Explicit `quinn::TransportConfig` from required env vars (`MH_MAX_CONCURRENT_UNI_STREAMS`, `MH_DATAGRAM_BUFFER_AUDIO_FRAMES` converted once to bytes via `NOMINAL_AUDIO_FRAME_BYTES` — the ~225 B on-wire nominal frame derived from media-protocol's size constants plus a documented Opus payload constant, never the max-payload DoS ceiling nor the bare codec payload; `MH_KEEPALIVE_INTERVAL_MS`; explicit non-None datagram receive buffer); `MH_MAX_CONNECTIONS` required and relabelled a resource guard; startup validation (egress queue bound < transport ceiling; grace > margin); drain = `min(SETTLE_TARGET, grace − MARGIN)` from kustomize-derived `MH_TERMINATION_GRACE_SECONDS`. RegisterMeeting applies policy through a config-apply mailbox separate from lifecycle, publishes a lock-free routing snapshot, echoes the applied generation, enforces monotonicity and idempotency, echoes transport mode with loud mismatch; dead `route_media`/`stream_telemetry`/`register` handlers removed and `mh_grpc_requests_total{method}` collapses to `register_meeting`. New `src/media/` holds only the hot path (ingress loop → snapshot lookup → 6-byte relay rewrite at constant offset → egress via the trait); setup/apply/lifecycle/teardown are siblings. Ingress caps before allocation; bounded ingress and egress queues (drop-oldest) with `mh_media_frames_dropped_total{reason}` including `egress_queue_overflow` (a §1 queue, never "budget"); decomposed sampled latency through cached handles; `key_custody=operator`; per-frame tracing feature is a release `compile_error!`.

### client
`sdk-core` gains the v2 codec (drift-guarded `max_payload_bytes` from the vectors file; zero-copy; reserved bits rejected) and a three-module crypto stack — RFC 9605 §4.4 key schedule (HKDF-SHA512, 64-byte PRK, direct GCM derivation), SFrame seal/open with detached tag, framing with the deliberate deviations (AAD = publisher region only; signed range = publisher‖payload; both as slices of the received buffer; publisher region fully populated before slicing) — plus KEK unwrap (nonce = zero-padded BE64 key id, AAD = key id) and Ed25519 via WebCrypto with `@noble/ed25519` fallback. Receive path: verify (key from `key_id.sender_id` via roster; no self-trust branch) → replay window advancing on verified frames only → unwrap accepted only for the carrying frame's key id, never cached from an unverified frame → decrypt → Opus decode → play. Capture via `getUserMedia` + WebCodecs Opus at 32 kbps/20 ms; client mute at capture; transmit key per (sender, stream, generation) rotated every T and on resume, carried wrapped on every audio frame; bounded SDK egress queue with send-drop counter; `MediaTransport` gains datagram send/receive. Media metrics carry `client_version`, `org_id`, `key_custody=operator` only — never `...this.#metricLabels` (which carries `meeting_id_hash`; `MediaTransport.ts:284`). `frames_received` counts at the wire. Web app: in-meeting view with visible mute indication and device select; Svelte stores via `bindMeetingSession`; browser env-test with fake-device flags asserting loopback audio (latency observed), structural mute (egress count flat), unmute resume. Runbook subsection `## Secure Context and Media Setup` lands first as the shared anchor.

### protocol
P1 header v2 in `media-protocol` with derived size constants (`AEAD_TAG_BYTES`, `KEY_ID_BYTES` atomics; `WRAPPED_TRANSMIT_KEY_SIZE`, `SFRAME_OBJECT_OVERHEAD_BYTES` derived), `MAX_PAYLOAD_BYTES`, shared reject-reason vocabulary, fuzz corpus regenerated. P2 `proto/test-vectors/frame-v2.vectors.json` with a non-production Rust reference generator (computes AAD span, signed range, detached-tag split from the spec, never by mirroring TS), external sframe-wg 0x0005 vectors vendored at commit 025d568 for the key schedule, drift guard in the pipeline, tamper pair, insider-forgery (decrypts-if-unverified), wrap-binding mismatch, four AAD-span combinations, one full_frame row; carries the ADR-0027/ADR-0036 HKDF-SHA512 amendment. P3 signalling reshape (layout messages and single-key EncryptionKeys deleted; media-kind enum collapsed; receive-capability with optional per-slot pin; seven slot states; send directive with target set carrying transport mode; stream assignment keyed by numeric `sender_id`; JoinRequest identity key; JoinResponse KEK + generation + `sender_id`; roster `identity_public_key`; HostMute → server mute; KEK-push defined unused). P4 internal reshape (RouteMedia, participant Register, StreamTelemetry deleted with evidence; RegisterMeeting request = repeated self-contained `EgressStream` + `selection_rules` + generation; response = applied generation, handler id, process-start epoch, transport-mode echo; no `server_muted`; `max_streams` untouched). Wire invariant recorded at the key-id definition: *a key id is never reused under one KEK — generation monotonic per sender and never reset, and `sender_id` never recycled while a KEK is live.*

### infrastructure
I-1 fixes `dt-guard env-config` discovery and multi-ConfigMap resolution (hard-fail on undiscoverable workloads; removes four orphan OTel keys with rationale moved to TODO). I-2 lands the three §1 transport keys (unit in the name), explicit `MH_MAX_CONNECTIONS`, kustomize-derived `MH_TERMINATION_GRACE_SECONDS` (verified against kustomize v5.7.1: deleting the source field fails the build), an env-test asserting the deployed value equals the pod spec, and comments distinguishing three max-named keys including the known-wrong, deferred `MH_MAX_STREAMS`. I-3 builds the deny-guard mechanism (config-driven directory list, macro families including span/instrument, cached-handle allow-list, distinct scope-missing/scope-empty failure tokens; fixtures dir and self-test placement fixed) — depends on MH's media directory existing. I-4 asserts the release-profile premise and hard-fails `dev-web.sh` preflight on MH unreachability, with a secure-context pointer.

Every piece of media-path state is in memory or in-frame by design; no migration in this or any later ADR-0036 story may persist KEK, transmit-key, or identity-key material (database will flag any that does). Verified against MC (no Postgres use), GC `participants` and `media_handlers`, AC `signing_keys` (AC's own keys, unrelated). Later-story schema note: `media_handlers.max_streams/current_streams` is the story-2 egress-budget concern.

## Cross-Cutting Requirements

### Security
Mandatory checklist (security):
1. **Authentication** — client↔MH: meeting JWT at WebTransport accept (EdDSA via JWKS, `token_type == "meeting"`); MC↔MH registration: OAuth client-credentials bearer with `service.write.*` scopes. No new externally reachable endpoint; the risk is the new ingress/egress loops sitting outside the gate → R-20.
2. **Authorization** — meeting-scoped token; admission is the authorization; MC hands the KEK only to a participant it admitted. Server mute and per-edge permissions are out of v1 scope.
3. **Input validation** — frame header (R-6), wrapped transmit key (R-13), raw signing key at join (R-11, load-bearing since it is the only validation on that field this story), receive-capability slot cap (R-18); unknown flag bits rejected in the binary codec (protobuf preserves unknown fields, so fail-closed lives in the codec).
4. **Data protection** — KEK, transmit keys, identity private key; nothing stored at rest; QUIC/TLS on every hop plus SFrame between clients; MC must not echo the KEK anywhere but the join response.
5. **Error handling** — R-17's counterpart: no error path emits frame contents, key material, key ids, or participant identifiers to logs, error bodies, or the UI; existing MH/MC/GC sanitisation preserved.
6. **Cryptography** — `ring::rand::SystemRandom` / `crypto.getRandomValues`; AES-256-GCM, Ed25519, HKDF (SHA-512 added to ADR-0027 by this story); nonces synthesised, never transmitted; no custom constructions.

Findings accepted: (1) the loopback self-recognition shortcut → R-4; (2) the client→GC edge is a method change, deferred with attestation, with the naming floor; (3) no insecure-origin Chrome flags → R-33; (4) vocabulary entries cannot be cited as KEK protection → R-23's directory deny.
