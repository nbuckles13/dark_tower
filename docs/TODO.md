# Technical Debt

## Inter-Service Protocol Inconsistency

- [ ] **AC internal APIs use HTTP/JSON without shared contracts**: All other inter-service communication (GC↔MC, GC↔MH, MC↔MH) uses gRPC with proto-defined contracts in `proto/internal.proto`. AC is the exception — its internal APIs (`/api/v1/auth/internal/meeting-token`, `/api/v1/auth/internal/guest-token`, `/api/v1/auth/token`) are HTTP/JSON with request/response structs defined independently on each side. This caused a production-visible bug: GC's `MeetingTokenRequest` defined `home_org_id: Option<Uuid>` while AC's expects `home_org_id: Uuid` (required), resulting in 422 errors at runtime. No compile-time check catches these mismatches. Options: (a) migrate AC internal APIs to gRPC and add to `internal.proto`, or (b) create a shared `ac-api-types` crate that both AC and GC import. The `common::token_manager` (OAuth token fetch) is already shared but the meeting/guest token request types are not. Locations: `crates/gc-service/src/services/ac_client.rs` (GC's structs), `crates/ac-service/src/models/mod.rs` (AC's structs).

- [ ] **`RejectionReason` lacks an `INVALID_REQUEST` variant**: `proto/internal.proto:189-194` defines `RejectionReason` as `UNSPECIFIED|AT_CAPACITY|DRAINING|UNHEALTHY`. When MC's `AssignMeetingWithMh` rejects a malformed request (e.g., empty `mh_assignments` or empty `MhAssignment.grpc_endpoint`), the handler at `crates/mc-service/src/grpc/mc_service.rs:248-251` maps the `McError::InvalidArgument` to `RejectionReason::Unhealthy`, which is misleading — MC is healthy, GC sent bad data. GC consumers may interpret this as a transient MC issue and retry, which won't help. Add `REJECTION_REASON_INVALID_REQUEST` and route invalid-argument paths to it. Low frequency (GC contract violations should never happen), but the right semantic for observability and correct GC behavior under bug conditions.

## Devloop Container Resource Hygiene & Build Isolation

Surfaced 2026-06-29 during task #10's (GC telemetry env-test backfill) Gate 2: the
host-side cluster build exhausted disk mid-`COPY` ("no space left on device"), and
`podman system prune -af` reclaimed **~2 TB**. Investigation found three distinct,
operations/infrastructure-owned problems. None are env-test scope; captured here as
the operations brief. Related: see "Skip unchanged service image builds" under
§Developer Experience (the `.dockerignore` / build-context-narrowing half).

- [ ] **(B — CORRECTNESS, highest priority) Concurrent same-host devloops share `localhost/{ac,gc,mc,mh}-service:latest` → wrong-code-in-cluster race.** Every other per-devloop resource is namespaced by slug — clone (`devloop.sh:79`), dev/db containers (`:80-81`), network (`:132`), helper dir (`:95`), Kind cluster `devloop-${TASK_SLUG}`, ports — but the image build/load layer is **global**: `build_image localhost/gc-service:latest` (`infra/kind/scripts/setup.sh:531/552/590/655`), the manifests hard-pin that tag (`infra/services/*/deployment.yaml:34` etc.), and `load_image_to_kind` does `podman save localhost/gc-service:latest` → `kind load --name $CLUSTER_NAME` (`setup.sh:160-168`), saving whatever the **host** `:latest` points to at that instant. There is **no lock/serialization** (`grep flock|lock|mutex` → 0 hits). Race with two slugs A,B building concurrently: (1) A builds → host `:latest`=A; (2) B builds → host `:latest`=B and B's `build_image` `rmi`s A's image id (`setup.sh:289-290`); (3) A's `podman save` now saves **B's binary** and loads it into **A's** cluster → A silently runs B's code. Masked today only because (i) once `kind load`ed each cluster has its own copy (race window = build→save→load) and (ii) devloops may not actually overlap on one host — but "runs the wrong code when they do" is a latent data-corruption bug, not a disk issue. **Fix:** per-slug image tags `localhost/gc-service:${TASK_SLUG}` across `setup.sh` build+load + a kustomize `images:` transformer in `overlays/kind/` to rewrite `:latest`→`:${slug}` at deploy (manifests hard-pin `:latest`). - [ ] **(A — the ~2 TB leak) Service images + build cache are never garbage-collected.** The only GC in the flow is `build_image` removing the *previous same-tag* image (`setup.sh:289-290`; twin at `devloop.sh:59-62/419-422`) — it never touches build cache, and a *failed* build (the `rmi` runs only after success) leaves partial layers + cache with zero cleanup (we saw 2 failed setups in `helper.log` 02:44/02:52). `cleanup()` (`devloop.sh:126-167`) tears down containers + network + Kind cluster + clone but **not** the host service images or `COPY`-context build cache — the one resource class it builds but never reclaims.   ### Exposure

  **Production exposure nil** — none of the six packages is in the prod graph or a shipped bundle; they are test runner, linter, build plugins and the Nx CLI. Both SDK packages are `private: true`, so there is no downstream publish/supply-chain surface either. Residual risk is **developer-workstation and CI-runner only**.

  `@vitest/browser`'s CRITICAL is a Browser-Mode file-access permission-gate bypass — a test-runner sandbox escape, not a product vulnerability, and only while browser-mode tests run. **The 9.4 vector is AV:N and needs network access to the Browser Mode API.** Neither `packages/sdk-svelte/vitest.config.ts` nor `packages/web-app/vitest.config.ts` sets `test.api` / `api.host`, and nothing in the repo passes `--host` or `0.0.0.0`, so Browser Mode binds its loopback default.   ### Verification must not rely on `pnpm audit` going green

  Assert **installed versions directly** rather than treating a clean audit as proof:

An unfalsified inference does not sit still — it gets cited, and each citation makes it look better-sourced than it is.
