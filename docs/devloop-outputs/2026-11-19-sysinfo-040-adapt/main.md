## Planning

### Mechanism restatement
Instance: "`System::new_all()` now returns `Result`". Mechanism: **a resource-reading field on a GC heartbeat whose "no reading" state is indistinguishable from a real 0**. sysinfo 0.40 only made one of the failure paths fallible; the others were already silent:
1. `System::new()` Err (new in 0.40).
2. `refresh_memory()` is infallible; an unreadable `/proc/meminfo` leaves `total_memory() == 0`, and current code maps that to `memory_percent = 0`.
3. CPU usage is a delta between two refreshes; a fresh `System` per call has no baseline, so `global_cpu_usage()` is ~0 on *every* heartbeat today (the pre-existing bug). Also `cpus()` empty after refresh = no reading.
4. Wire: `ComprehensiveHeartbeatRequest.cpu_usage_percent`/`memory_usage_percent` are plain `float`, so MC *cannot* say "no reading" — any value sent is a fabrication.

Same-shape siblings outside MC: `SendLoadReportRequest` (MH -> GC) — MH hardcodes `0.0` for cpu/memory/bandwidth (`crates/mh-service/src/grpc/gc_client.rs:315`), and GC compensates with a `> 0.0 => Some` heuristic (`crates/gc-service/src/grpc/mh_service.rs:269`) that also discards a genuine 0 reading. GC only `debug!`-logs MC's readings; MH's go to `media_handlers.*_usage_percent` (nullable columns).

### MC side
- `system_info.rs`: replace `gather_system_info()` with a long-lived `SystemSampler` owned by the GC task. Holds `Option<System>`; constructed with `System::new()` (not `new_all` — we need CPU + memory only, not processes/disks); on Err it records the error and **retries init on the next sample** (no panic: readings are advisory telemetry, the MC serves meetings fine without them). Each `sample()` does `refresh_cpu_usage()` + `refresh_memory()` and returns `SystemReadings { cpu: Result<f32, ReadingUnavailable>, memory: Result<f32, ReadingUnavailable> }` with `ReadingUnavailable::{InitFailed, CpuBaselinePending, NoCpus, NoMemoryTotal}`. CPU is `Ok` only when the previous CPU refresh was >= `sysinfo::MINIMUM_CPU_UPDATE_INTERVAL` ago (so the persistent `System` gives a real 30s delta; first tick after start is `CpuBaselinePending`). Pure classification split from the sysinfo calls so every reason is unit-testable without a broken host.
- `main.rs`: sampler built once at GC-task start (primed). On each comprehensive tick, each unavailable reading -> `mc_system_readings_unavailable_total{reading=cpu|memory, reason}` + `warn!` (`CpuBaselinePending` at `debug!`, expected once per process start). Heartbeat health stays `Healthy`: a telemetry gap is not service unhealth (GC would otherwise drain an MC that serves fine).
- `metrics.rs` + catalog: the new counter. Labels bounded (2 x 4).
- Tests: classification per reason, percent clamping, sampler returns a real CPU reading on the second sample after `MINIMUM_CPU_UPDATE_INTERVAL` (persistent-baseline regression for the always-0 bug), metric emission via `MetricAssertion`.

### Wire: Option A (Lead decision)
- `internal.proto`: make these fields `optional float`:
  - `ComprehensiveHeartbeatRequest.cpu_usage_percent` / `memory_usage_percent` (4/5)
  - `SendLoadReportRequest.cpu_usage_percent` / `memory_usage_percent` / `bandwidth_usage_percent` (4/5/6)
  Field comments: unset means no reading; a set value is a measurement in [0, 100]. Same tags and types plus presence, so the change is wire-compatible in both directions (operations; buf breaking rc=0 measured by protocol). Any rollout order is safe and each service rolls back independently. Per the Lead, there are no mixed-version tests or affordances. The comments state both the sender obligation and what the receiver does (protocol wording): "Senders MUST NOT set a non-finite value or one outside [0, 100]; a receiver discards such a value and treats it as no reading." The discard applies only to that field; the rest of the request still applies. The request does not fail with INVALID_ARGUMENT.
- MC sends `Some(v)` only for an available reading. `gc_client.comprehensive_heartbeat` takes `Option<f32>`.
- MH sends `None` for all three readings, because it measures nothing. This replaces the fabricated `0.0` with an honest absence.
- **GC: field-level discard (Lead ruling at Gate 1; raised by operations, agreed by security and global-controller).** Rejecting the whole report would put advisory telemetry in charge of MH liveness. `update_load_report` sets `last_heartbeat_at`, and staleness drives selection and replacement, so a single bad reading could migrate live meetings.
  - GC adds one helper, `grpc/mod.rs::sanitize_usage_percent(source, field, sender_id, Option<f32>) -> Option<f32>`. It returns no `Status`, and both handlers call it.
    - `None` passes through.
    - `Some(v)` with `v.is_finite() && (0.0..=100.0).contains(&v)` passes through.
    - Any other value becomes `None`. It is never clamped or saturated. GC logs a `warn!` with `controller_id`/`handler_id` (the sender id), `source`, `field`, `reason` and `raw_value` as log fields, never as labels, and increments `gc_usage_readings_discarded_total{source=mc|mh, field=cpu|memory|bandwidth, reason=non_finite|out_of_range}`.
  - Labels are bounded, and no id or raw value is ever a label. Only the reachable series are pre-registered at zero: (mc x cpu|memory) and (mh x cpu|memory|bandwidth), each x 2 reasons, for 10 series. mc x bandwidth cannot occur and is never registered.
  - The counter gets a catalog entry in `gc-service.md`. The entry lists the 10 series and states:
    - mc x bandwidth cannot occur.
    - There is no alert, because this is advisory telemetry. A non-zero rate means a peer bug; investigate it from the warn log.
    - The MC-side counterpart is `mc_system_readings_unavailable_total`. `source=mc` stays at 0 unless MC has a bug, because MC filters invalid values before sending.

    It also gets a panel on `gc-overview.json`: `sum by (source, field, reason) (increase(gc_usage_readings_discarded_total[$__rate_interval]))`, using counter presentation per ADR-0029, with editorMode and range set explicitly.
  - `current_streams` still rejects the whole request with `InvalidArgument`, because it is a placement input.
  - `mh_service.rs` runs all three readings through the helper and passes the resulting `Option`s to `update_load_report`. A real 0 is stored as 0, and `None` (including a discarded value) is stored as NULL. The UPDATE overwrites the column with no COALESCE, because the latest report had no valid reading.
  - `mc_service.rs` runs both readings through the helper and logs the resulting `Option`.
  - Tests: see §Test list, GC.

### MC sender-side value rules (security condition 2, test points 2 and 4)
- A pure classifier `classify(raw) -> SystemReadings`. Its inputs are the raw cpu `f32`, the cpu count, `used`/`total` memory as `u64`, and the baseline age.
- Rules:
  - total memory of 0 -> `NoMemoryTotal`
  - no cpus -> `NoCpus`
  - baseline younger than `MINIMUM_CPU_UPDATE_INTERVAL` -> `CpuBaselinePending`
  - a non-finite or negative value -> `InvalidValue`, never clamped (`f32::min(NaN, 100.0)` is 100, which would be a fabrication)
  - a finite value above 100 -> `InvalidValue` (Gate-3 Lead ruling on observability F1, replacing the planned clamp: clamping 150% to 100% would fabricate a reading and disagree with GC's discard rule)
  - `used > total` -> `InvalidValue`
- Readings stay `f32` end to end. The `u32` truncation goes, since the wire field is a float.
- `ReadingUnavailable` = `InitFailed | CpuBaselinePending | NoCpus | NoMemoryTotal | InvalidValue`. It is an MC-local enum, not an `McError` variant: it describes a single reading being absent, not an operation failing. It is also the one reason vocabulary for the metric label (DRY point 3).
- The heartbeat-side decision is lib code, not inline in the `select!` arm. `SystemReadings::to_wire() -> (Option<f32>, Option<f32>)` plus `record_unavailable()` (metric + log); `main.rs` only calls `sampler.sample()` and passes the result through. A unit test asserts that an `Err` reading becomes `None` and never `Some(0.0)`.
- The old tests that only exercise Clone/Debug or construct the struct directly are replaced by behavioural tests. No test asserts cpu > 0. The persistent-baseline test asserts that a second sample taken after `MINIMUM_CPU_UPDATE_INTERVAL` is not `CpuBaselinePending` (a real ~200ms sleep).

### Test list (agreed with test, code-reviewer, observability, GC, protocol)
- **MC classifier (pure, no sleeping):**
  - baseline age: `None` -> `CpuBaselinePending`; MIN-1ns -> Pending; exactly MIN -> Ok.
  - memory: total 0 -> `NoMemoryTotal`; used == total -> 100; used > total -> `InvalidValue`.
  - cpu: 0 cpus -> `NoCpus`; NaN/inf/negative/above 100 -> `InvalidValue`; exactly 0 and 100 are real readings.
- **MC sampler, with init injected as a closure (`System::new` in prod):**
  - Init Err -> both readings `InitFailed`. Init then Ok -> the next sample really attempts the readings and does not stay stuck in `InitFailed`.
  - After a re-init, CPU restarts as `CpuBaselinePending`, because the baseline timestamp is reset.
- **MC real-host regression (one test):** sample, sleep `MINIMUM_CPU_UPDATE_INTERVAL`, sample again. Assert `cpu.is_ok()` and that the value is finite and in 0..=100. Never assert > 0.
- **MC per-tick lib fn (`SystemReadings` -> wire + metric/log), via `MetricAssertion`:**
  - Every `Err`, including `InvalidValue`, becomes `None` on the wire.
  - Each counted reason increments `{reading, reason}` by exactly 1, with at least one reason per reading.
  - `CpuBaselinePending` emits nothing.
  - Mixed result (cpu Ok, memory `NoMemoryTotal`) -> `(Some(v), None)` and exactly one memory increment.
- **MC `gc_integration`:** the comprehensive request carries `Some` values, plus a `None` case.
- **MH:** the load report is built with `None` for all three fields.
- **GC (field-level discard, see Wire):**
  - `mh_service` discard cases. Each sends `Some(NaN)`, `Some(+/-inf)`, `Some(-1.0)` or `Some(100.5)` in a report that has a valid other field and a new `current_streams`, after a prior valid `Some` for the same field. Each asserts:
    - the response is Ok;
    - the invalid field is NULL;
    - the other fields are stored;
    - `current_streams` is updated;
    - `last_heartbeat_at` has advanced;
    - via `MetricAssertion`, exactly the expected `gc_usage_readings_discarded_total{source, field, reason}` series moved by 1.
  - `mh_service` accepted values: `Some(0.0)` is stored as 0, and `Some(100.0)` is accepted.
  - `mh_service` no reading: `None` sent after `Some(x)` stores NULL.
  - `mh_service` overflow: the existing `current_streams` overflow test still expects `InvalidArgument`.
  - `mc_service`: `None` is accepted for both fields. One invalid value is discarded and counted with `source=mc`, and the heartbeat still succeeds.
- **Not added:** a prost round-trip test and mixed-version tests (Lead ruling). The derive-only tests are deleted along with `gather_system_info`.

### Observability
- Counter: `mc_system_readings_unavailable_total{reading=cpu|memory, reason=init_failed|no_cpus|no_memory_total|invalid_value}` (the catalog states that `no_cpus` occurs only with `reading=cpu`, that `no_memory_total` occurs only with `reading=memory`, and that one init failure increments both the cpu and the memory series; `cpu_baseline_pending` is not counted, see below).
- Logs:
  - init failure: `warn!(target: "mc.system_info", error = %e, error_kind = unsupported|io|other)`, repeated every 30s while init keeps being retried, with no rate limit

One `const fn label()` on `ReadingUnavailable` and one on `Reading` is the single source for both the metric labels and the log fields. No alert, and the catalog records why: the readings are advisory, GC does not place on them, and so there is no actionable response. With no alert, no runbook change is needed.

## Implementation Summary

- **Proto**: `ComprehensiveHeartbeatRequest` 4/5 and `SendLoadReportRequest` 4/5/6 are now `optional float`. Each message's leading comment states the presence and range rule and the sender MUST clause, and each field has a one-line comment saying what it measures.
- **MC** (`system_info.rs`): `gather_system_info` is replaced.
  - New types: a long-lived `SystemSampler` (`System::new()`, refreshing only CPU usage and memory, with init injectable as a test seam), the pure `classify(&RawSample)`, `SystemReadings::{to_wire, record_unavailable}`, and `Reading` / `ReadingUnavailable` with `label()`, which is the single source for both metric and log values.
  - Init failure logs a warn with `error` and `error_kind`, reports both readings as `InitFailed`, and is retried on the next sample. A successful re-init resets the CPU baseline.
  - The CPU baseline mirrors sysinfo's own gate: the last effective refresh advances only when sysinfo actually refreshed.
  - `main.rs` owns one sampler per GC task. `gc_client.comprehensive_heartbeat` now takes `Option<f32>`.
- **MC metric**: `mc_system_readings_unavailable_total{reading, reason}`. The 6 reachable series are zero-initialized. Added a catalog entry and an MC Overview panel.
- **MH**: the load report sends all three readings unset.
- **GC**: one `grpc/mod.rs::sanitize_usage_percent` helper is used by both handlers.
  - An invalid reading becomes `None`, is never clamped, and logs a warn with `controller_id` (mc) / `handler_id` (mh), `source`, `field`, `reason` and `raw_value`. The rest of the request still applies.
  - The `> 0.0` heuristic is removed.
  - New metric `gc_usage_readings_discarded_total{source, field, reason}`. The 10 reachable series are zero-initialized. Added a catalog entry and a GC Overview panel.
- **Docs**: rewrote the TODO entry and updated the MC INDEX pointer.

4. **Safe-revert unit**: the whole commit. Each service also rolls back independently on the wire (proto3 `float`→`optional float` is compatible both ways), but a partial *source* revert would leave a Rust caller mismatched against the generated `Option<f32>` types and fail to compile.

## Issues Encountered & Resolutions

**Problem**: the implementer re-ran `layer-fast.sh` after reporting ready while the Lead's fast check was running. `layer-all.sh` clears `/tmp/devloop/layer-*.log` at start, so the Lead's run got rc=2 with no Layer-3 status.

**Resolution**: it passed 3/3 standalone and did not recur in the Lead's runs. It was attributed to the concurrent-run load in Issue 1, so it is not tracked.

## Lessons Learned

1. A dependency bump that turns an infallible call into a `Result` is worth tracing past the call site. Here it exposed three other silent-zero paths, including CPU reading ~0 on every heartbeat, and a wire contract that could not express "no reading".
2. Whole-request rejection on a message that also carries liveness couples liveness to advisory data. Validate advisory fields per field.
3. Shared `/tmp/devloop` means only one `layer-*` run at a time per tree.
