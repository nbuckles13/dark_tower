## Task Overview

### Objective
When MC's `AssignMeetingWithMh` handler rejects a **malformed** request (empty `mh_assignments`, or an `MhAssignment` with an empty `grpc_endpoint`), it currently maps `McError::InvalidArgument` onto `RejectionReason::UNHEALTHY`. GC treats UNHEALTHY as a transient controller problem: the assignment loop pushes the MC onto `tried_mcs`, logs "will retry", and walks the rest of the pool. Every MC rejects the identical malformed request the same way, so the retry budget is spent proving nothing, and the failure is finally recorded as "rejected: unhealthy" — reporting a sick MC fleet when the real fact is that GC sent bad data.

Add a `REJECTION_REASON_INVALID_REQUEST` variant, route the invalid-argument paths to it, decide + justify GC's handling (fail fast vs retry), and make the log line and metric label say the request was **invalid** rather than that a controller was unhealthy.

### Scope
- **Service(s)**: MC (mapping), GC (mirror enum + loop handling + observability labels), proto (additive enum variant)
- **Schema**: No
- **Cross-cutting**: Yes — proto contract (GSA), MC producer, GC consumer, observability labels

### Debate Decision
NOT NEEDED — scope is one additive enum variant + its mapping/handling/labels within existing boundaries. The taxonomy is not being redesigned; AT_CAPACITY/DRAINING/UNHEALTHY semantics are untouched. The one genuine decision (GC fail-fast vs retry) is delegated to the implementer to make and justify in the plan.

### 4. GC handling — **DECISION: fail fast, do not retry the pool** (`mc_assignment.rs`, mine)
**Justification.** INVALID_REQUEST means GC computed a malformed request (empty MH
selection or an MH with an empty `grpc_endpoint`) — a GC-side contract violation.
The request bytes are identical for every MC in the pool, so every MC rejects it
identically. Retrying across the pool cannot change the outcome; it only burns the
retry budget and, worse, ends by recording "rejected: unhealthy" — a false
sick-fleet signal. On the first INVALID_REQUEST rejection, GC **breaks the retry
loop immediately** (does not push to `tried_mcs`, does not walk the pool). This is
a deliberate behaviour change, scoped to this one variant; AT_CAPACITY / DRAINING /
UNHEALTHY keep walking the pool exactly as today.

The end-of-loop `match last_rejection_reason` (status/rejection_reason) is
exhaustive with no catch-all — the new variant produces the intended compile error;
I add a real arm `Some(InvalidRequest) => ("rejected", Some("invalid_request"))` and
add **no** catch-all.

**Returned error — DECISION: `GcError::Internal` (500), not `ServiceUnavailable`
(503).** A contract violation is a GC-internal defect, not a transient
unavailability; 503 tells the caller "retry, another server may work," which is the
exact false signal we are removing (retry recomputes the same bad selection). 500 is
the honest classification. Both are 5xx, so no SLO/alert selector changes. (Flagged
for @code-reviewer / @operations — trivially revertible to ServiceUnavailable if
they disagree.)

### Gate 3 findings — all FIXED in-changeset

- **@security S-3 (fail-fast trusted a remote claim; removed MC failover).** The original code
  broke the retry loop on `McRejectionReason::InvalidRequest` from the MC's word alone. A buggy or
  rolled-back MC returning `4` for a *well-formed* request could then veto assignment for the whole
  pool (failover removed), and a rogue MC could inflate the `invalid_request` series. **Fix (security's

## Lessons Learned

1. **Route a contested call to the owning specialist directly — never through a reviewer as relay.** Every relay round in the catalog churn produced another flip; three parties each held a different "final" at some point.
2. **A reviewer should hold a pointer to another specialist's decision, not a duplicate of it.** @operations circulated a Gate-2 invariant copied from a decision it didn't own; when the decision moved, the copy became a check that would have rejected the correct file. This is CLAUDE.md's single-source-of-truth rule playing out on the team rather than in the code.
3. **ACK/verify from the file, not from recollection of the decision.** Decisions converge while beliefs about file state diverge; the Gate-2 file-check is what dissolved the "who holds what" ambiguity.
4. **The Lead should enforce the owner-states-once-bindingly mechanism, not impose a value while the owner is still oscillating.** The Lead flipped its own catalog ruling once — worse than a reviewer doing it — and had to unwind it; the fix was to ratify the owner's binding statement, not to keep picking.
5. **Guards that scan the filesystem without respecting `.gitignore` false-positive on generated artifacts.** The subdomain-guard 13-vs-10 is the same "control checks the wrong target set" class as the GSA-glob-drift entries; the durable fix is `git ls-files`-scoped scanning.
6. **A hunk-ACK is only as good as its timestamp — ping the reviewer when an ACKed file is touched again** (@operations, after a post-ACK edit to `gc-alerts.yaml`). @implementer correctly did this.
7. **A one-way ANCHOR faces away from the party most likely to cause the drift.** For a producer↔validator coupling (GC `selection_is_malformed` ↔ MC `store_mh_assignments`) where divergence fails *silent into the original defect*, the reciprocal anchor must sit in front of the party where validation naturally grows (@dry-reviewer).
